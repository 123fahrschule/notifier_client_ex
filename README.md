# NotifierClient

Elixir client for sending E-Mail delivery commands to the 123Fahrschule Notifier service.

This first version supports E-Mail delivery only. SMS, Telegram, push notifications, and delivery-status consumers are intentionally out of scope for this change.

## Installation

Add the package to a service once it is published or referenced from Git:

```elixir
def deps do
  [
    {:notifier_client_ex, git: "git@github.com:123fahrschule/notifier_client_ex.git"}
  ]
end
```

The client uses Elixir's built-in `JSON` module by default and does not require Jason on modern Elixir versions. RabbitMQ publishing is handled through Tackle.

## Configuration

Configure the source service and RabbitMQ connection in the host application.
Application config is used by default, and the same keys can be passed per call as options to `NotifierClient.deliver/2` or `NotifierClient.send_email/2` for tests or one-off overrides.

```elixir
config :notifier_client_ex,
  source_service: "absence",
  rabbitmq_url: System.get_env("RABBITMQ_URL") || "amqp://localhost",
  publisher_connection_name: "Absence NotifierClient Publisher"
```

Core options:

- `source_service`: service name used for default CloudEvent `source` and `actor`. `"absence"` becomes `"de.123fahrschule:absence"`.
- `rabbitmq_url`: broker URL passed to the publisher adapter.
- `publisher_connection_name`: logical publisher connection name. With the default Tackle adapter, calls sharing this name share Tackle's pooled publisher connection.

Extension points:

```elixir
config :notifier_client_ex,
  publisher: NotifierClient.Publisher.Tackle,
  json_codec: NotifierClient.JSONCodec.BuiltIn,
  metadata_provider: NotifierClient.MetadataProvider.Default
```

## Publisher Configuration

The `publisher` option controls how the already encoded JSON payload is sent. The default is:

```elixir
config :notifier_client_ex,
  publisher: NotifierClient.Publisher.Tackle
```

`NotifierClient.Publisher.Tackle` publishes through Tackle using the publish options generated by the client:

```elixir
[
  rabbitmq_url: "...",
  exchange: "notifier",
  routing_key: "deliver-email",
  publisher_connection_name: "..."
]
```

Custom publishers must implement this callback:

```elixir
@callback publish(payload :: binary(), options :: keyword()) ::
            :ok | {:error, term()}
```

The library includes `NotifierClient.Publisher.Stub` as a reference implementation for tests. It captures publish calls as messages without opening a RabbitMQ connection:

```elixir
config :notifier_client_ex,
  publisher: NotifierClient.Publisher.Stub
```

Then assert on the published payload and publish options:

```elixir
assert :ok = NotifierClient.send_email(email)

assert_receive {:notifier_client_published, payload, options}
assert options[:exchange] == "notifier"
assert options[:routing_key] == "deliver-email"
assert JSON.decode!(payload)["type"] == "de.123fahrschule:notifier:deliver-email"
```

The stub returns `:ok` by default. Publisher error handling can be tested with:

```elixir
NotifierClient.Publisher.Stub.put_result({:error, :unroutable})

assert {:error, :unroutable} =
         NotifierClient.send_email(email, publisher: NotifierClient.Publisher.Stub)

NotifierClient.Publisher.Stub.clear_result()
```

If the publish call happens in another process, configure the receiver in that process:

```elixir
test_pid = self()

task =
  Task.async(fn ->
    NotifierClient.Publisher.Stub.put_receiver(test_pid)
    NotifierClient.send_email(email, publisher: NotifierClient.Publisher.Stub)
  end)

assert :ok = Task.await(task)
assert_receive {:notifier_client_published, payload, options}
```

The delivery APIs return the publisher result unchanged. If the publisher returns `{:error, :unroutable}`, `send_email/2` returns `{:error, :unroutable}`.

## JSON Codec Configuration

The `json_codec` option controls how the Notifier event map is encoded before it is passed to the publisher. The default is:

```elixir
config :notifier_client_ex,
  json_codec: NotifierClient.JSONCodec.BuiltIn
```

`NotifierClient.JSONCodec.BuiltIn` uses Elixir's built-in `JSON.encode!/1`. This is the preferred default for modern Elixir versions and avoids a hard Jason dependency.

Custom JSON codecs must implement this callback:

```elixir
@callback encode!(term()) :: binary()
```

Example Jason adapter for a host application that intentionally wants to use Jason:

```elixir
defmodule MyApp.NotifierJasonCodec do
  @behaviour NotifierClient.JSONCodec

  @impl true
  def encode!(term), do: Jason.encode!(term)
end
```

Configure it globally:

```elixir
config :notifier_client_ex,
  json_codec: MyApp.NotifierJasonCodec
```

Or override per call:

```elixir
NotifierClient.send_email(email, json_codec: MyApp.NotifierJasonCodec)
```

## Metadata Provider Configuration

The `metadata_provider` option controls the CloudEvent-like top-level fields around the email payload: `id`, `source`, `specversion`, `time`, `actor`, `datacontenttype`, `causation_id`, and `correlation_id`.

The default is:

```elixir
config :notifier_client_ex,
  metadata_provider: NotifierClient.MetadataProvider.Default
```

`NotifierClient.MetadataProvider.Default`:

- Generates an event id when none is provided.
- Builds `source` from `source_service`.
- Uses explicit `actor` or `enacted_by`, otherwise the source.
- Uses explicit `time` or `occurred_at`, otherwise current UTC time.
- Defaults `causation_id` to `"#{event_type}:#{event_id}"`.
- Defaults `correlation_id` to the causation id.
- Sets `specversion` to `"1.0"` and `datacontenttype` to `"application/json"`.

Metadata can be passed directly on the email:

```elixir
email =
  email
  |> NotifierClient.Email.metadata(
    event_id: "domain-event-id",
    actor: "de.123fahrschule:absence",
    causation_id: "de.123fahrschule:absence:daily-reminder:123",
    correlation_id: "de.123fahrschule:absence:daily-reminder:123"
  )
```

Or per delivery call:

```elixir
NotifierClient.send_email(email,
  metadata: [
    event_id: "domain-event-id",
    correlation_id: "correlation-id"
  ]
)
```

Custom metadata providers must implement this callback:

```elixir
@callback build(
            metadata :: map(),
            config :: NotifierClient.Config.t(),
            context :: map()
          ) :: map()
```

The provider must return a map with string keys for the top-level event fields the Notifier contract expects. The `context` currently includes `:event_type`.

Example provider that delegates to existing shared helpers:

```elixir
defmodule MyApp.NotifierMetadataProvider do
  @behaviour NotifierClient.MetadataProvider

  @impl true
  def build(metadata, config, %{event_type: event_type}) do
    event_id = metadata[:event_id] || Shared.UUID.generate()
    source = "de.123fahrschule:#{config.source_service}"
    causation_id = metadata[:causation_id] || "#{event_type}:#{event_id}"

    %{
      "id" => event_id,
      "source" => source,
      "specversion" => "1.0",
      "time" => DateTime.to_iso8601(metadata[:occurred_at] || DateTime.utc_now()),
      "actor" => metadata[:actor] || metadata[:enacted_by] || source,
      "datacontenttype" => "application/json",
      "causation_id" => causation_id,
      "correlation_id" => metadata[:correlation_id] || causation_id
    }
  end
end
```

Configure it globally:

```elixir
config :notifier_client_ex,
  metadata_provider: MyApp.NotifierMetadataProvider
```

The library also includes `NotifierClient.MetadataProvider.Shared`, a light optional bridge. It uses `Shared.UUID.generate/0` when that module exists in the host application and otherwise falls back to the default provider behavior.

## E-Mail Usage

Build E-Mail commands with small composable functions:

```elixir
email =
  NotifierClient.Email.new()
  |> NotifierClient.Email.idempotency_key("de.123fahrschule:absence:pending-absence-reminder:employee-1:2026-06-26")
  |> NotifierClient.Email.template("absence/team-leads/daily_reminder_of_absence_pending_requests")
  |> NotifierClient.Email.to("teamlead@example.com")
  |> NotifierClient.Email.from("info@123fahrschule.de")
  |> NotifierClient.Email.subject("Pending absence requests")
  |> NotifierClient.Email.put_placeholder("pending_requests_count", 3)
  |> NotifierClient.Email.priority(:high)

NotifierClient.send_email(email)
```

`NotifierClient.deliver(email)` is equivalent to `NotifierClient.send_email(email)`.

The idempotency key is serialized to Notifier as `email_delivery_request_identifier`. It should be deterministic for the triggering business action so retries do not create duplicate delivery requests. `NotifierClient.Email.delivery_request_id/2` is available as an alias for `NotifierClient.Email.idempotency_key/2`.

### Email builder API

`NotifierClient.Email` commands are immutable structs. Every builder function returns an updated command and can be chained:

- `new/0`: starts a new email command.
- `idempotency_key/2`: sets the deterministic delivery request identifier.
- `delivery_request_id/2`: alias for `idempotency_key/2`.
- `template/2`: sets the Notifier email template slug.
- `to/2`: appends one or more `to` recipients.
- `cc/2`: appends one or more `cc` recipients.
- `bcc/2`: appends one or more `bcc` recipients.
- `from/2`: sets the sender address.
- `reply_to/2`: sets the reply-to address.
- `subject/2`: sets the email subject.
- `put_placeholder/3`: adds or replaces one placeholder.
- `put_placeholders/2`: merges multiple placeholders at once.
- `deliver_at/2`: schedules delivery for a `DateTime`.
- `priority/2`: sets the delivery priority.
- `attach_s3/4`: adds an Amazon S3 attachment.
- `metadata/2`: merges multiple event metadata fields.
- `put_metadata/3`: adds or replaces one event metadata field.

Recipient functions accept a single email address, a `{name, address}` tuple, or a list of either form:

```elixir
email
|> NotifierClient.Email.to("teamlead@example.com")
|> NotifierClient.Email.cc(["cc1@example.com", "cc2@example.com"])
|> NotifierClient.Email.bcc({"Team Archive", "archive@example.com"})
```

Placeholders can be added one at a time:

```elixir
email
|> NotifierClient.Email.put_placeholder("pending_requests_count", 3)
```

Or merged in one call:

```elixir
email
|> NotifierClient.Email.put_placeholders(%{
  "first_name" => "Ada",
  "pending_requests_count" => 3
})
```

Placeholder keys must be strings. Atom keys such as `:pending_requests_count` are rejected by validation because Notifier placeholders are serialized as string-keyed JSON object fields.

Supported priorities are:

- `:highest` / `"highest"`
- `:high` / `"high"`
- `:default` / `"default"`
- `:low` / `"low"`
- `:lowest` / `"lowest"`

Amazon S3 attachments can be added with:

```elixir
email
|> NotifierClient.Email.attach_s3(
  "https://s3.example.com/file.pdf",
  "application/pdf",
  "file.pdf"
)
```

Metadata can also be set through the email builder:

```elixir
email
|> NotifierClient.Email.metadata(
  event_id: "domain-event-id",
  correlation_id: "correlation-id"
)
|> NotifierClient.Email.put_metadata(:actor, "de.123fahrschule:absence")
```

With the default and shared metadata providers, metadata keys may be atoms or strings. Custom metadata providers receive the metadata map unchanged and decide which key conventions they support.

## Public API Reference

Delivery:

- `NotifierClient.send_email/2`: encodes and publishes an email command.
- `NotifierClient.deliver/2`: generic delivery entry point; currently supports `NotifierClient.Email`.

Email event helpers:

- `NotifierClient.Email.Event.type/0`: returns the Notifier email event type.
- `NotifierClient.Email.Event.subject/0`: returns the Notifier email event subject.
- `NotifierClient.Email.Event.to_event/2`: validates an email command and returns `{:ok, event}` or `{:error, %NotifierClient.ValidationError{}}`.
- `NotifierClient.Email.Event.to_json/2`: validates an email command and returns `{:ok, json, event}` or `{:error, %NotifierClient.ValidationError{}}`.

Configuration and metadata:

- `NotifierClient.Config.get/1`: resolves application config plus per-call overrides.
- `NotifierClient.Config.publish_options/2`: builds publisher options for a command type.
- `NotifierClient.Metadata.build/3`: delegates metadata envelope creation to the configured metadata provider.
- `NotifierClient.MetadataProvider.Default.build/3`: builds the default event metadata envelope.
- `NotifierClient.MetadataProvider.Shared.build/3`: uses `Shared.UUID.generate/0` when available, otherwise follows the default provider behavior.
- `NotifierClient.Identifier.uuid/0`: generates a UUIDv4 string.
- `NotifierClient.Identifier.source_urn/1`: converts a service name such as `"absence"` to `"de.123fahrschule:absence"`.

Validation and encoding:

- `NotifierClient.Email.Validator.validate/1`: validates an email command and returns `:ok` or `{:error, %NotifierClient.ValidationError{}}`.
- `NotifierClient.ValidationError.message/1`: formats validation errors for exception messages.
- `NotifierClient.JSONCodec.BuiltIn.encode!/1`: encodes terms through Elixir's built-in `JSON.encode!/1`.

Publisher adapters:

- `NotifierClient.Publisher.Tackle.publish/2`: publishes an encoded JSON payload through Tackle.
- `NotifierClient.Publisher.Stub.publish/2`: captures a publish call in the current process for tests.
- `NotifierClient.Publisher.Stub.message_tag/0`: returns `:notifier_client_published`.
- `NotifierClient.Publisher.Stub.put_receiver/1`: sends captured publish messages to another process.
- `NotifierClient.Publisher.Stub.clear_receiver/0`: clears the process-local receiver.
- `NotifierClient.Publisher.Stub.put_result/1`: configures the process-local result returned by `publish/2`.
- `NotifierClient.Publisher.Stub.clear_result/0`: clears the configured process-local result.

Behaviours for custom integrations:

- `NotifierClient.Publisher.publish/2`: callback for publisher adapters.
- `NotifierClient.JSONCodec.encode!/1`: callback for JSON codecs.
- `NotifierClient.MetadataProvider.build/3`: callback for metadata providers.
